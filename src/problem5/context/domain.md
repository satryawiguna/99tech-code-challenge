# Problem 5 — Domain Model

## 1. Purpose

This document defines the domain model for Problem 5 based on the approved discovery findings.

The purpose of this document is to establish the meaning, boundaries, attributes, lifecycle, and domain rules of the resource before API and database design.

The selected domain is an engineering decision. The 99Tech challenge does not prescribe a specific business domain or resource.

---

## 2. Domain Scope

### Selected Domain

**Support Ticket Management**

### Primary Resource

**Ticket**

The system is intentionally limited to the lifecycle and persistence of a single primary resource: `Ticket`.

The domain does not attempt to model a complete customer-support platform.

---

## 3. Domain Boundary

The Ticket domain is responsible for:

- representing a support ticket;
- maintaining ticket details;
- maintaining ticket status;
- maintaining ticket priority;
- supporting ticket lifecycle changes;
- providing data required for CRUD operations;
- supporting basic filtering by domain-relevant attributes.

The Ticket domain is not responsible for:

- user authentication;
- user registration;
- authorization and role management;
- customer identity management;
- ticket comments;
- file attachments;
- notifications;
- email delivery;
- real-time communication;
- external support integrations.

These capabilities remain outside the domain scope unless a later requirement explicitly requires them.

---

## 4. Ticket Entity

The primary domain entity is:

```text
Ticket
```

Initial conceptual model:

```text
Ticket
├── id
├── title
├── description
├── status
├── priority
├── createdAt
└── updatedAt
```

The conceptual model does not prescribe the final database column types or API serialization format. Those decisions belong to the API and database design phases.

---

## 5. Ticket Attributes

### 5.1 `id`

**Purpose**

Uniquely identifies a Ticket.

**Domain characteristics**

- required;
- immutable after creation;
- unique within the Ticket collection;
- generated by the system rather than supplied as an authoritative identifier by the client.

The exact identifier format will be decided during architecture and persistence design.

---

### 5.2 `title`

**Purpose**

Provides a concise summary of the issue represented by the Ticket.

**Domain characteristics**

- required;
- must not be empty;
- must contain meaningful text;
- subject to a defined maximum length at the API validation boundary.

The exact maximum length will be finalized during API design.

---

### 5.3 `description`

**Purpose**

Contains the detailed description of the issue represented by the Ticket.

**Domain characteristics**

- required for Ticket creation;
- must contain meaningful text;
- subject to appropriate input-size constraints.

The exact length constraints will be finalized during API design.

---

### 5.4 `status`

**Purpose**

Represents the current lifecycle state of the Ticket.

Initial domain values:

```text
open
in_progress
resolved
closed
```

`status` is a server-controlled domain value.

A newly created Ticket always starts with:

```text
status = open
```

The client does not provide the initial status during Ticket creation.

---

### 5.5 `priority`

**Purpose**

Represents the relative urgency of the Ticket.

Initial domain values:

```text
low
medium
high
```

`priority` is a domain-controlled value and must always contain one of the supported values.

The client may provide the priority during Ticket creation and update it later, subject to the API and domain validation rules.

---

### 5.6 `createdAt`

**Purpose**

Records when the Ticket was created.

**Domain characteristics**

- assigned by the system;
- immutable after creation;
- represents the creation timestamp.

The exact timestamp representation will be finalized during architecture and database design.

---

### 5.7 `updatedAt`

**Purpose**

Records when the Ticket was most recently modified.

**Domain characteristics**

- assigned and maintained by the system;
- updated whenever persisted Ticket details change;
- must not be supplied as an authoritative value by the client.

---

## 6. Ticket Lifecycle

The initial Ticket lifecycle is:

```text
open
  ↓
in_progress
  ↓
resolved
  ↓
closed
```

The lifecycle represents the intended progression of a support ticket.

However, the challenge only requires CRUD operations and does not explicitly require a workflow engine.

Therefore, the implementation should not introduce complex workflow orchestration.

The application must at minimum ensure that `status` contains a valid domain value.

Any strict transition restrictions will only be implemented if they are justified during architecture and implementation design.

---

## 7. Domain Rules

### DR-01 — Ticket Identity

Each Ticket must have a unique system-generated identifier.

### DR-02 — Required Title

A Ticket must have a non-empty title.

### DR-03 — Required Description

A Ticket must have a description when a Ticket is created.

### DR-04 — Initial Ticket Status

Every newly created Ticket must have:

```text
status = open
```

The initial status is assigned by the server and cannot be overridden by the client during creation.

### DR-05 — Valid Status

A Ticket status must be one of:

```text
open
in_progress
resolved
closed
```

### DR-06 — Valid Priority

A Ticket priority must be one of:

```text
low
medium
high
```

### DR-07 — System-Controlled Timestamps

`createdAt` and `updatedAt` are maintained by the system.

### DR-08 — Creation Timestamp Immutability

`createdAt` must not change after Ticket creation.

### DR-09 — Modification Timestamp

`updatedAt` must reflect the latest persisted modification to the Ticket.

### DR-10 — Identifier Immutability

A Ticket identifier must not change after creation.

---

## 8. Create Semantics

Creating a Ticket requires the client to provide the domain data necessary to establish a valid Ticket.

Initial required creation data:

```text
title
description
priority
```

The server is responsible for:

```text
id
status = open
createdAt
updatedAt
```

The initial status of every newly created Ticket is `open`.

The exact create payload and validation rules will be finalized during API design.

If additional defaults are introduced, they must be documented explicitly rather than inferred by clients.

---

## 9. Update Semantics

The initial API design proposes partial updates using:

```text
PATCH /api/v1/tickets/:id
```

An update may modify mutable Ticket attributes such as:

```text
title
description
status
priority
```

The following attributes are not client-controlled:

```text
id
createdAt
updatedAt
```

`updatedAt` is updated by the server when a persisted modification occurs.

The final update payload and validation rules will be defined in the API contract.

Any strict status-transition rules remain subject to the final architecture and API design.

---

## 10. Delete Semantics

Deleting a Ticket removes the Ticket from the active resource collection.

The initial domain model does not introduce soft-delete semantics.

A soft-delete mechanism would add additional state and persistence behavior that is not required by the challenge.

If later requirements justify retaining deleted records, that decision must be explicitly documented rather than introduced implicitly.

---

## 11. Filtering Semantics

The Ticket collection supports basic filtering by domain-relevant attributes.

Initial supported filter candidates:

```text
status
priority
```

Examples:

```text
status=open
```

```text
priority=high
```

```text
status=open&priority=high
```

Filtering is intended to narrow the collection returned by the list operation.

Filtering does not modify domain state.

The exact query syntax and response metadata will be defined during API design.

---

## 12. Domain Invariants

The following conditions must remain true for every persisted Ticket:

```text
1. id is unique.
2. id does not change after creation.
3. title is not empty.
4. description is valid according to the domain's input constraints.
5. status is a supported domain value.
6. priority is a supported domain value.
7. createdAt is assigned by the system.
8. createdAt does not change after creation.
9. updatedAt is maintained by the system.
```

Additionally, every newly created Ticket must satisfy:

```text
status = open
```

These invariants should be protected regardless of whether the operation originates from an HTTP API or another internal application component.

---

## 13. Domain Validation Concepts

The domain must distinguish between invalid domain data and valid operations that cannot be completed because the target resource does not exist.

### Invalid Ticket State

A Ticket contains a status or priority value that is not supported by the domain.

### Invalid Ticket Data

Required Ticket data does not satisfy domain constraints.

### Missing Ticket

A requested Ticket does not exist.

A missing Ticket is an application/use-case condition rather than a domain invariant.

The application layer is responsible for translating this condition into the appropriate API behavior.

The exact error codes, HTTP status codes, and response format belong to the API contract and are intentionally not finalized here.

---

## 14. Domain and Persistence Separation

The domain model describes what a Ticket means.

It does not prescribe:

- a specific database engine;
- SQL table names;
- ORM models;
- database indexes;
- migration tooling;
- repository implementation.

Those concerns belong to the persistence and architecture design.

For example:

```text
Domain
  Ticket
    ↓
Application
  Ticket use cases
    ↓
Persistence
  Database representation
```

The database representation should preserve the domain invariants defined in this document.

---

## 15. Domain and API Separation

The domain model does not prescribe the complete HTTP contract.

The API layer will determine:

- endpoint paths;
- HTTP methods;
- request schemas;
- response schemas;
- HTTP status codes;
- query parameters;
- error response format.

The API must nevertheless preserve the domain rules and invariants defined here.

## 17. Explicit Non-Goals

The domain model intentionally does not define:

- users;
- agents;
- organizations;
- comments;
- attachments;
- notifications;
- authentication;
- authorization;
- billing;
- SLA management;
- escalation workflows;
- external integrations.

These may exist in a real-world support system but are intentionally excluded from this challenge implementation.

The approved domain direction is:

```text
Support Ticket Management
        ↓
      Ticket
        │
        ├── Identity
        │     └── id
        │
        ├── Details
        │     ├── title
        │     └── description
        │
        ├── Classification
        │     ├── status
        │     └── priority
        │
        └── Metadata
              ├── createdAt
              └── updatedAt
```

The domain is intentionally limited to one primary resource and the minimum rules necessary to support a reliable CRUD service.
